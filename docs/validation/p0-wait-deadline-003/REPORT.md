# P0 MFM：已复现原生450秒截止，确认服务器等待预算不兼容

2026-10-31，WSL Ubuntu 24.04。只读MFM副本成功完成初始化，随后原生long_poll在450.000874秒触发本地`native_timeout`；外层470秒RPC收到失败回复，桥接映射为`NotConnected`。同版本服务器软件的静态调用链确认：请求timeout=400时，名义订阅超时为400＋服务器当前time对90取余，即400～489秒。**现有450秒总截止小于服务器允许的等待预算，是已确认的兼容性缺陷。** 尚未发布修复，也不将所有历史离线样本归为这一原因。

## 实验身份与过程

诊断源码基于干净提交`1285aa08832dfb4f706a5bd013dae7e0f8163598`，仅在一次性目录增加阶段日志及将外层RPC设为470秒；原生请求内容、450秒原生截止和产品恢复路径保持。二进制哈希见[manifest.json](manifest.json)，不是已安装的`.6`二进制，也不是开发包。原六个冻结任务不重启、不共享此实例的可写数据库；NAS范围只读。

沿用MFM 91,033节点副本及12条权限排除项。预先限定初始化最多300秒、在线后观察最多900秒，首个终止错误即结束；初始化失败和停止错误分别记录，不删除此前[002失败](../p0-wait-deadline-002/REPORT.md)。实际未用满900秒，因捕获终止错误而结束。

| 阶段 | 实测 | 含义 |
|---|---:|---|
| 从观察器开始到online＋mounted | 89.159563秒 | 包含初始化期间状态调用；观察器在解锁后启动，与阶段日志起点不同，不能与下两项直接相加 |
| RecoverySnapshot RPC | 86.255417秒 | 由bridge阶段时间差测得；含服务器枚举、传输和worker处理，不能全归为网络延迟 |
| 本地快照安装阶段 | 5.180837秒 | 含取得Store锁、失效项准备和数据库安装，尚未细分锁等待/SQL耗时 |
| 第一轮long_poll | 30.360ms | changes=0、profile_changed=true，正常响应；没有输出profile值 |
| 第二轮本地发送完成 | 154µs | 库级发送结束，不等价于独立证实服务器已经收到 |
| 第二轮原生请求结束 | 450.000874秒 | `native_timeout`，未收到完整最终响应或keep_alive帧 |

初始化样本保留了调用错误和connecting状态，没有删除慢样本。本轮正常停止不关闭002初始化期间停止超时，也不关闭更早固定夹具退出超时；三个阶段不同。仅检查了状态接口、进程和阶段日志，没有在超时瞬间验证文件正文读取。

## 服务器端的等待规则

输入是此前经授权只读取得的Drive Server 4.0.3-27892 `syncd`软件副本。本次重新读取本地文件并验证SHA-256 `e2288b191e8db97673c3468595e3a2d441579d2da365927c1108c000549fdf9c`；没有再次连接SSH、修改NAS、读取用户数据库或执行服务器二进制。版本来源及提取方法见[server/manifest.json](server/manifest.json)。

| 证据 | 已确认行为 |
|---|---|
| [LongPollHandler::Handle](server/function-3ff8c0.asm)，0x3fffc0～0x40002b | 读取timeout，转换为Int16；当前请求的400可沿此路径进入ebx |
| 同函数0x3ffc60～0x3ffcab | 调用time，经过高位乘法/移位计算对90取余，再把余数加到timeout，作为Subscriber构造参数。它是时间相关偏移，不是随机数 |
| [Subscriber构造](server/function-53f460.asm)，0x53f4bf～0x53f4c9 | 再取time，并加上该秒数预算，保存订阅到期时间 |
| [IsTimeout](server/function-53f6a0.asm)，0x53f6aa～0x53f6b3；[HandleSubscriptions](server/function-5433f0.asm)，0x5435b0～0x5436de | 根据当前秒数与到期时间判断；到期或相应强制路径调用SendTimeoutResponse |
| [SendTimeoutResponse](server/function-53fde0.asm)，0x53fe92～0x53ffcf | 构造response、空changes数组及alive=150，经WriteHeader发送。不是仅凭函数名称把超时当断开 |

取余归纳另以20,000个非负输入检查高位乘法公式，均与`time % 90`一致。这个检查验证算术归纳，不是服务器运行测试。400～489是无事件路径的名义预算；有变化可以提前返回，排队、调度及系统时钟可能改变实际响应耗时，不能宣称489秒是所有情况下的硬上限。

本次未捕获服务器接收时的time值，也没有等到450秒以后的服务器响应，所以不能宣称“本次服务器必定准备在488秒返回”。可以确认的是：native确实在450秒自己结束了等待，而这个截止在协议允许的等待区间之内。前一轮约428秒正常响应与此区间一致，但不能反推它必然是超时空响应。

## 官方客户端参照及修复边界

[官方Linux静态报告](../p0-official-timeout-static-001/REPORT.md)确认客户端为通道设置600秒，并在底层读到数据后刷新计时；收到keep_alive继续等待。当前native的两层450秒绝对截止既小于合法订阅预算，也没有保活进展语义。本次没有观察到keep_alive，故不声称此次失败由保活处理错误造成。

后续需用新隔离实验验证合法的超过450秒响应及取消/重连边界，再形成产品修改：区分服务器订阅预算、底层无进展超时和外层RPC截止，避免外层先结束仍有效的请求；同时保持FUSE本地目录与缓存可用。不能只忽略超时错误、把离线状态强制显示在线，或无限等待掩盖真实网络故障。产品修改与新开发包需通过对应回归和发布门禁；本轮仅诊断和静态证据，不进入性能通过或候选通过状态。

132项协议单元测试＋2项文档测试通过，1项文档测试忽略；这是诊断构建回归，没有全产品/GUI重跑。导出核验原六个FUSE主PID和`.6`哈希保持。24小时观察器在归档时为第1251轮、11个失败样本、约3.48小时，仍需完整窗口及审查。
