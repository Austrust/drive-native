# 只读缓存句柄的同步与关闭隔离

2026-10-31，本批修复已打开完整缓存文件在正文读取结束后，仍因 `fsync`、`flush` 或 `release` 排入元数据队列而等待 Store 的问题。

## 路由与持久化边界

仅当同一短句柄表锁内确认 `ino/fh` 匹配、打开标志为 `O_RDONLY` 且当前内容为 `Cached` 时，采用无写入快路径：

- `flush/fsync` 没有该句柄的本地写入需要提交，可立即完成，不取 Store、不访问网络、不唤醒上传。
- `release` 在同一锁内移出句柄，随后由独立读取队列释放本地引用。队列拒绝时任务析构仍释放引用；已经捕获内容的读取者继续通过 `Arc` 保护旧完整版本。
- 路由完成后不再查询表中内容，因此不会把后来晋升为 Draft 的句柄送入读取队列再等待 Store。

Draft、可写句柄以及 Missing 内容保留元数据路径。可写 Draft 仍执行 `checkpoint_draft` 与 `creation_saved`；只读 Draft 仍执行原有 `creation_saved`。慢路径执行时才重新读取句柄内容，保留并发晋升语义。

慢路径 release 使用析构清理守卫，正常执行和队列拒绝均不遗留关闭句柄。初始判定和最终清理都校验 inode；错误 inode 返回 `EBADF`，不能删除对应另一 inode 的真实句柄。拒绝任务仍遵循既有 EIO 行为，不伪造保存成功。

## 已执行验证

全部使用独立 WSL 普通用户、临时目录和合成文件，没有 NAS、真实账号或基线数据访问。

1. 将新增内核回归与 `2629ca6` 原 `writable.rs` 配对：四个元数据工作线程被 Store 屏障阻塞时，只读缓存读取后的 `sync_all/close` 在 2 秒内未完成，回归按预期失败；随后先解除屏障再清理测试挂载。
2. 相同屏障下，修复后的 1 MiB 读取、`sync_all`、重复描述符关闭和最终关闭完成；最后一次合成运行约 **4.70 ms**。Store 尚未解锁时句柄已清除，上传唤醒次数为零。这是依赖隔离回归的单次耗时，不是混合性能 p95。
3. 可写 Cached、可写 Draft 和被晋升的只读 Draft 的 `fsync` 仍等待元数据屏障；解锁后成功，重新打开 Store 可读取已提交的修改。
4. 路由测试覆盖错误 inode、晋升前后分类、队列饱和拒绝清理，以及 release 后仍由读取者引用保护的缓存内容。

5. 对未 checkpoint 的可写 Draft，分别注入元数据队列满、测试内容目录不可写两种故障。真实 `close` 返回 `EIO`，没有上传唤醒；句柄和 Draft 引用释放后，数据库仍保留 dirty 标记，垃圾回收不删正文，内容哈希保持一致。重新打开 Store 并恢复 checkpoint 后，上传操作仍为 PendingUpload，不能显示已同步。这验证了关闭失败后的本地恢复，不把失败的保存称为已持久确认，也未验证突然断电。
